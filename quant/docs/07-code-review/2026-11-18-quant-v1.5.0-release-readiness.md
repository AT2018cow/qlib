## 回滚目标和适用条件

针对 v29 引入的回归，备用目标是在同一维护窗口将 Daily、Website 配对恢复到原 v28 部署，代码为 `31b65fa8ac722bdaa975eadde604f181621314af`。两套 App 的 v28 版本和提交已在部署历史中核对。v28 源码包含相同的四个调度，已发布的 v28/v29 网站产物的三市场语义与账户合同哈希一致。v28 已有 11 月 12 日 FULL 补跑和 11 月 13 日自然增量证据。v29 在 v28 基础上调整了调度来源记录及校验。`quant-v1.3.0` 保留为历史发布版本。

生产故障优先按现有调度恢复或前向修复。仅在确认属于 v29 回归、得到生产变更授权、且两套 App 没有在途发布调用时，在同一个维护窗口依次切换 Website 和 Daily。先核对授权的生产 profile 与 environment，并确认工作区套餐支持原生回滚。原生回滚命令如下。[Modal 回滚文档](https://modal.com/docs/guide/managing-deployments#deployment-rollbacks)

```sh
modal app rollback qlib-prod-website v28
modal app rollback qlib-prod-daily v28
```

Modal 会写入一条新的部署历史。若工作区不支持原生命令，从冻结的 `31b65fa8a` 干净检出，按授权生产部署配置依次前台部署 Website 和 Daily，并检查镜像与挂载。切换后应回读两套 App 的目标源码、调度、资源和 Volume 挂载，再按目标源码校验 Provider、journal、网站收据和 marker。两套 App 必须使用相同源码，v29 marker 会因源码身份校验在 v28 下被拒绝。需要恢复当前业务日期时，复用合法的 Provider 与已发布 journal，使用获批的 coordinator 恢复流程补齐目标源码下的网站收据和 marker，然后做只读核验。保留 Git 历史、Volume、现有账户账本与归档。此次只核对了回滚目标和命令，生产回滚演练待单独安排。
